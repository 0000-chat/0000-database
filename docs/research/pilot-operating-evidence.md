# Pilot operating evidence: Worker plus per-database SQLite Durable Object

_Research date: 2026-09-15. Scope: bounded export, replay capacity, admission and cleanup. Vendor facts are labelled; design conclusions and open measurements are separate._

## Decision supported

The settled implementation target is a Worker routing each opaque database slug to one SQLite-backed Durable Object (DO), serializing database mutations. Feasibility of materializing every admitted database within platform CPU, wall-time and storage limits remains unmeasured. A DO serializes one invocation and transaction, but does not make a transaction or cursor atomic across `await`s or requests. A consistent multi-request export therefore needs an export-owned snapshot at start; an admitted database cannot silently receive weaker live pagination.

## Proposed bounded export

At `start_export`, the database DO takes its normal serialization gate and opens one SQLite transaction. It copies the database description, schema, indexes and records into rows keyed by a fresh `exportId`, recording one `snapshotAt`. It commits the complete materialization before returning the handle. Every later `read_export` is a bounded read of those immutable rows, with a cursor bound to `exportId`, database ID, and format version. No transaction, SQLite cursor, or lock crosses an HTTP/MCP request boundary. A concurrent writer therefore lands either before the materialization transaction or after it, never partly in the export.

Materialization is itself bounded work. Reserve export bytes and row count before the transaction; reject with `RESULT_TOO_LARGE` when the candidate snapshot exceeds the published cap, and with `CAPACITY_UNAVAILABLE` when the reserved pool is full. Keep export rows in a separate internal namespace so normal database quota accounting and export retention can be observed independently. `expiresAt` is a hard retention deadline; after it, reads return `EXPORT_EXPIRED`. An export page stays within the 256 KiB ordinary response bound and should normally be smaller to leave protocol overhead. The export guarantee must cover every database admitted under the published 10 MiB quota. If one transaction cannot materialize that maximum within measured CPU/wall limits, investigate a versioned or point-in-time snapshot mechanism or reopen the product contract; do not silently lower the cap or substitute several live transactions while claiming consistency.

## Replay and creation-key capacity

Keep completed mutation outcomes for 24 hours from completion, indexed by database ID and canonical operation key. Store a request digest plus the smallest sufficient logical outcome; retain the response representation when exact cross-transport replay requires it. Reserve the worst-case bytes before committing the mutation. A reused key while running returns `REQUEST_IN_PROGRESS`; a different canonical request returns `IDEMPOTENCY_CONFLICT`; a replay does not execute, renew inactivity, or consume another mutation allowance.

The approved 100-mutations-per-UTC-day quota can yield 200 successful outcomes in a rolling 24-hour window spanning two UTC dates. At the contract's 256 KiB response ceiling that is 50 MiB of replay response payload before indexes and metadata. Retaining canonical 64 KiB requests as well would add up to 12.5 MiB; prefer a digest unless the request is required to reconstruct the logical result. These are conservative bounds, not measured workload sizes. Creation keys need a separate global 24-hour namespace because a create can be retried before its database slug is known; reserve its entries and response bytes before creating the database. If either reserve is exhausted, reject before committing work, so the 24-hour promise remains true.

The accepted anonymous-pilot budget target is US$25 per month. It is a planning target, not a customer-facing price or a guarantee of the total invoice. Cloudflare's published storage and row figures do not by themselves cover request and duration compute charges, Worker routing, or internal export/replay amplification; the final budget model requires measured workload data.

## Service admission, cleanup and inactivity

Use a service-wide admission state with separate budgets for ordinary work, export materialization/read, replay retention, and cleanup. When the ordinary pool is suspended, reject new ordinary operations with `CAPACITY_UNAVAILABLE`. A new export start is allowed only after acquiring the reserved export materialization and retention budget; existing export reads and cleanup use their already-reserved allowances and drain. Per-database quota rejection is different: it neither pauses the seven-day inactivity countdown nor renews it. A successful data read or write renews it; metadata polling, failed requests and idempotent replays do not. A successful export operation should be classified explicitly as a data read before release, rather than relying on an accidental route classification.

Because alarms may overlap requests, cleanup must use the same per-database serialization gate (or a lease/version check) before deleting expired export and replay rows. Process bounded batches, reschedule while work remains, and finish each alarm under the 15-minute platform ceiling. Track reserved bytes until deletion is confirmed; cleanup lag must reduce admission before physical capacity is exceeded. During a service-wide capacity suspension, persist the suspension interval and exclude it from inactivity age calculations. The 30-day write cutoff continues to advance, and a database's own quota exhaustion does not create a pause.

## Prototype pass/fail criteria

1. **Snapshot consistency:** start an export, perform schema and record writes between export pages, then read all pages. Pass only if every page has the same `snapshotAt` and schema, IDs are neither duplicated nor missing, and no post-start change appears. An expired handle must return `EXPORT_EXPIRED`; a deliberately over-cap snapshot must fail before a partial handle is visible.
2. **Atomicity and bounded work:** inject a failure during materialization. Pass only if the database is unchanged and no usable partial export exists. Measure transaction wall time, CPU, rows, serialized bytes, SQLite file-size delta, cursor memory, and request/response sizes at increasing snapshot sizes; publish the largest size that stays below the selected safety margins. Record exact `transactionSync` availability and all observed SQL limits.
3. **Replay:** submit the same mutation key through REST and MCP during execution and at several points before 24 hours. Pass only if the mutation occurs once and the logical outcome matches; a changed canonical request conflicts; after expiry, no automatic retry guarantee is claimed. Fill the replay pool to its worst-case reservation and verify the next mutation is rejected before commit.
4. **Alarm and lifecycle:** force expired export/replay rows and run cleanup with concurrent requests. Pass only if no live row is deleted, cleanup is resumable and bounded below 15 minutes, reserved bytes fall only after confirmed deletion, and ordinary admission reacts before the cap. Simulate service suspension and own-quota rejection separately; only the former pauses inactivity.
5. **Global admission and recovery:** run concurrent creates, mutations, export starts, replay reservations and cleanup leases near every ceiling. Pass only if live usage plus leases and reservations stays within budget, races cannot commit after reserve failure, and lease expiry fails closed. Restart Worker/DO during materialization and reservation; uncertain work must leave no partial export or double mutation. A crash after creation commit must be recovered by retrying the same key to the same slug for 24 hours; a removed database must not be recreated.

These tests are the release gate for exact export lifetime, SQL work caps, replay storage reservation, alarm cadence and the physical-to-logical 10 MiB relationship. None of those values is proven by the vendor documentation above.
